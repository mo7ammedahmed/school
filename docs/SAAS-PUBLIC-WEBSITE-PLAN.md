# خطة مواقع المدارس ضمن SaaS

الحالة: خطة للمراجعة فقط — لم يبدأ التنفيذ.
التاريخ: 2026-10-05.

## النتيجة المطلوبة

تملك كل مدرسة موقعًا عامًا مستقلًا، ويدير مدير المدرسة شكله ومحتواه من لوحة
مدرسته: القالب، الشعار، الألوان، الخطوط، الصور، الأقسام، الصفحات، القوائم،
بيانات التواصل ومحركات البحث. تبقى بيانات الطلاب والموظفين الداخلية والمسودات
خاصة، وتُعزل إدارة مدرسة عن جميع المدارس الأخرى.

مثال تصوري للعناوين، وليس إعدادًا حاليًا:

- موقع المنصة: `platform.example`.
- بوابة الإدارة المركزية: `app.platform.example`.
- موقع مدرسة: `alnoor.platform.example`.
- نطاق مخصص لاحقًا: `www.school.example`، بعد التحقق من ملكيته وتجهيز HTTPS.

## ما يمكن إعادة استخدامه

- نموذج `School` يتضمن الاسم، الرابط المختصر، الهوية والألوان وإعدادات المظهر.
- `UserMembership` يتضمن المدرسة والدور والصلاحيات وحالة العضوية.
- `TenantContext` و`TenantScope` و`BelongsToSchool` يوفرون أساس عزل السجلات.
- `EnsureSchoolContext` يتحقق من عضوية المستخدم في المدرسة المختارة.
- محرر الصفحات يدعم الأقسام، الترتيب، اللغتين، الإخفاء، النشر والمعاينة الخاصة.
- إعدادات المظهر والواجهة العامة تستخدم متغيرات ألوان المدرسة.
- `school_admin` لديه حاليًا `manage-content` و`manage-settings` ضمن تعريف الأدوار.

هذه أساسات قابلة لإعادة الاستخدام، وليست إثباتًا لاكتمال عزل SaaS.

## الفجوات المؤثرة

1. `SchoolResolver` يقرأ المدرسة من الجلسة، ثم يرجع إلى أول مدرسة. لا يحدد
   الموقع العام حسب نطاق المدرسة. كما يجب ألا تغير جلسة زائر مسجل الدخول
   هوية مدرسة أخرى يتصفح موقعها العام.
2. صلاحيات الإدارة تحتاج مراجعة لتكون محسوبة من العضوية والدور داخل المدرسة
   الحالية؛ امتلاك صلاحية في مدرسة لا يمنحها في مدرسة أخرى.
3. تحرير صفحة منشورة يحفظ التغييرات مباشرة في النسخة العامة. نحتاج مسودة
   مستقلة، وإصدارات منشورة واسترجاع إصدار سابق.
4. ملفات الهوية تُرفع حاليًا في مسار عام مشترك؛ نحتاج ملكية ملفات واضحة
   وفصل الملفات العامة عن الخاصة وربط اختيار الصور بالمدرسة.
5. يلزم تدقيق الطلبات العامة، الكاش، روابط التفاصيل، النماذج، المهام الخلفية
   وSSR/Octane على سياق مدرسة واحد، دون بقايا من طلب سابق.

## القرارات المقترحة

- المدرسة هي وحدة العزل الأولية باستخدام `school_id`. يظل ربط المدارس
  بالمؤسسة قائمًا؛ إدارة عدة مدارس تتطلب عضوية أو تفويضًا واضحًا لكل مدرسة.
- إعادة استخدام قاعدة البيانات الحالية مع تقوية العزل والقيود والاختبارات.
  فصل قواعد البيانات مستقبلًا قرار مستقل إذا تطلبه الحجم أو متطلبات العميل.
- البدء بعنوان فرعي لكل مدرسة، وإضافة النطاقات المخصصة بعد نجاح العزل.
  تُراجع إمكانات Laravel Cloud الفعلية للنطاقات والشهادات قبل اعتماد طريقة الربط.
- لوحة الإدارة المركزية تعرض المدرسة النشطة بوضوح. الموقع العام يحدد المدرسة
  من النطاق المسجل، مستقلًا عن جلسة المستخدم.
- اختيار قوالب جاهزة ومحرر أقسام منضبط في النسخة الأولى. تُخصص الألوان
  والخطوط والمسافات والأزرار، دون السماح بتنفيذ JavaScript أو HTML غير موثوق.
- تغيير مظهر الموقع العام لا يغير مظهر بوابة الإدارة تلقائيًا. يمكن توفير
  اختيار واضح لتوحيد الهوية بينهما لاحقًا.

## تجربة مدير المدرسة

قسم واحد في اللوحة باسم **موقع المدرسة** يحتوي على:

| الشاشة | ما يتحكم فيه المدير |
| --- | --- |
| الهوية والقالب | الشعار، الأيقونة، قالب الصفحة، الخطوط، ألوان الوضعين |
| الرئيسية | الصورة الرئيسية، النص، زر التقديم، الأقسام وترتيبها |
| الصفحات والقوائم | إنشاء الصفحات، عرضها أو إخفاؤها، ترتيب التنقل والتذييل |
| الأخبار والفعاليات | المحتوى والصور وتوقيت النشر |
| مكتبة الصور | ملفات المدرسة العامة ومواضع استخدامها |
| التواصل والقبول | بيانات التواصل، جهة استلام الرسائل، روابط ونماذج المدرسة |
| محركات البحث | عنوان ووصف الصفحات، صورة المشاركة، خريطة الموقع |
| المعاينة والنشر | مسودة مستقلة، معاينة خاصة، نشر أو جدولة، استرجاع إصدار |
| عنوان الموقع | عنوان المدرسة وحالة التحقق من النطاق المخصص |

تُعرض معاينة للهاتف وسطح المكتب قبل النشر. عند إنشاء المدرسة يبدأ موقعها
كمسودة بقالب ومحتوى ابتدائي قابل للتعديل، دون نشر أرقام أو أسماء افتراضية.

## حدود الصلاحيات المقترحة

| المستخدم | المسموح |
| --- | --- |
| الزائر | محتوى المدرسة المنشور والمعلومات المعتمدة للنشر فقط |
| محرر الموقع | تعديل المحتوى ومعاينة المسودات في مدرسته؛ النشر بتفويض منفصل |
| مدير المدرسة | إدارة ونشر موقع مدرسته وهويته وملفاته؛ لا وصول لمدرسة أخرى |
| الطالب أو ولي الأمر أو المعلم | الصلاحيات التعليمية الحالية؛ لا إدارة الموقع إلا بتفويض محدد |
| مدير المنصة | إنشاء المدارس وإدارة الاشتراك والنطاقات والقوالب؛ دخول إدارة مدرسة يكون صريحًا ومسجلًا |

تقسم صلاحيات الموقع إلى تحرير المحتوى، النشر، إدارة المظهر وإدارة النطاقات.
تُراجع طريقة ربطها بالأدوار الحالية قبل إضافة صلاحيات جديدة. يجب فرض الحماية
في الخادم والاستعلامات والتحميلات، وليس بإخفاء عناصر الواجهة فقط.

## مراحل التنفيذ المستقبلية

### 1. حسم العزل والعناوين

- إعداد مصفوفة لمسارات المنصة والإدارة والمواقع العامة والنماذج.
- تحديد أي المسارات يتبع النطاق وأيها يتبع مدرسة الإدارة المختارة.
- تدقيق جميع النماذج والقيود والفهارس والصلاحيات التي تخص مدرسة.
- تصميم سجل نطاقات مرتبط بالمدرسة، مع نطاق فريد وحالة تحقق وتفعيل.

مخرج المرحلة: تصميم البيانات والمسارات والصلاحيات، وخطة ترحيل قابلة للمراجعة.

### 2. تحديد المدرسة من النطاق

- حل نطاق موثوق ومسجل إلى المدرسة قبل مشاركة بيانات Inertia والهوية وربط
  نماذج المسارات، ثم تثبيت `TenantContext` للطلب.
- النطاق غير المعروف أو غير المفعل لا يعرض أول مدرسة ولا مدرسة الجلسة؛
  يقدم استجابة مناسبة دون بيانات مدرسة أخرى.
- استخدام نفس السياق في الصفحات والتفاصيل ونموذج التواصل وطلب القبول.
- مراجعة تطبيع النطاقات والنطاقات الموثوقة والروابط الأساسية وإعادة التوجيه.
- الاحتفاظ بمسارات الفواتير الموقعة والتحقق من توافقها مع سياق المدرسة.
- تنظيف سياق المدرسة عند انتهاء العمل، خصوصًا مع Octane والعمال المستمرين.

مخرج المرحلة: عنوان مستقل لكل مدرسة، وهوية ثابتة سواء كان الزائر مسجلًا أم لا.

### 3. فرض الصلاحيات والملكية

- التحقق من العضوية الفعالة والصلاحية المطلوبة داخل المدرسة الحالية.
- منع فتح أو تعديل صفحة أو ملف أو نطاق مدرسة أخرى بتغيير المعرف أو الطلب.
- تدقيق استثناءات الاستعلام عبر المدارس وحصرها في وظائف المنصة المصرح بها.
- عدم إرسال المسودات والأقسام المخفية أو البيانات التعليمية الخاصة ضمن HTML
  أو بيانات Inertia أو حمولة SSR العامة.

مخرج المرحلة: اختبارات عزل ناجحة لمدرستين ومستخدمين بأدوار مختلفة.

### 4. محرر الموقع والهوية

- تجميع أدوات المظهر والمحتوى الحالية تحت **موقع المدرسة**.
- إضافة اختيار القالب والصور والخطوط وتخصيص الرأس والتذييل والأزرار.
- فصل إعدادات الموقع العام عن إعدادات بوابة الإدارة، مع ترحيل الهوية الحالية
  بحيث يبقى مظهر الموقع الحالي محفوظًا.
- حفظ الأقسام بمخطط بيانات معروف وإصدار للقالب، والتحقق من الروابط والصور.
- توحيد معاينة القالب وعرضه العام ليستخدما نفس المكونات والمتغيرات.

مخرج المرحلة: يستطيع مدير مدرسة تخصيص موقعه دون تعديل برمجي.

### 5. دورة النشر والملفات

- إنشاء مسودات وإصدارات منشورة مستقلة للمحتوى والمظهر؛ تبقى النسخة العامة
  الحالية حتى إجراء النشر صراحةً.
- توفير معاينة خاصة لا تُفهرس ولا تُخزن في كاش عام، وجدولة واسترجاع إصدار.
- تسجيل من عدّل ومن نشر ومتى، مع سياق المدرسة.
- تقسيم ملكية ومسارات الملفات حسب المدرسة، والتحقق من الملفات عند اختيارها.
- اعتبار ملفات المسودات والوثائق الداخلية خاصة؛ نشر الوسائط العامة المعتمدة
  فقط، دون كشف ملفاتها بمجرد تخمين عنوان التخزين.

مخرج المرحلة: تعديل آمن ومعاينة ثم نشر واضح، مع إمكانية الرجوع.

### 6. التشغيل والنطاقات

- تضمين المدرسة واللغة والإصدار المنشور في مفاتيح الكاش، وعزل حالات الزائر
  والإدارة، ومنع تخزين الجلسات أو المعاينات في CDN عام.
- التأكد من أن SSR يعرض الطلب الحالي فقط، وأن تبديل المدارس لا يترك هوية
  أو بيانات في عمليات Octane أو مهام الخلفية المستمرة.
- إنتاج الروابط وSEO وخريطة الموقع من النطاق الأساسي المعتمد لكل مدرسة.
- التحقق من ملكية النطاق المخصص قبل ربطه، وتجهيز HTTPS، ومنع تكرار الملكية
  ووضع إجراء واضح للفصل أو النقل دون استيلاء مدرسة أخرى عليه.
- حفظ سياق المدرسة في الرسائل والمهام الخلفية والنماذج وتحديد حدود الاستعمال.

مخرج المرحلة: تشغيل عدة مواقع دون تداخل في الهوية أو المحتوى أو الكاش.

### 7. إطلاق تدريجي

- تشغيل الميزة في بيئة اختبار بمدرستين لهما ألوان ومحتوى مختلفان.
- إعداد بيانات المدرسة الحالية وعنوانها صراحةً؛ إزالة الاعتماد على المدرسة
  الأولى من مسارات SaaS مع الحفاظ على الروابط الحالية أثناء الانتقال.
- البدء بمدارس تجريبية، مع نسخة احتياطية ومراقبة وخطة رجوع للنشر السابق.
- مراجعة الاشتراكات والباقات وحدود التخزين والنطاقات كمشروع تجاري لاحق،
  قبل إضافة الدفع والتجديد؛ هذه الخطة لا تختار بوابة دفع أو أسعارًا.

## شروط قبول النسخة الأولى

1. تعديل شعار أو لون أو نص مدرسة «أ» لا يغير موقع مدرسة «ب».
2. كل نطاق يعرض مدرسته حتى عندما يزوره مدير مسجل في مدرسة أخرى.
3. مستخدم مدير في «أ» ومعلم في «ب» لا يرث إدارة «ب» من دوره في «أ».
4. تغيير معرف صفحة أو ملف أو مدرسة لا يمنح وصولًا خارج الصلاحيات.
5. المسودة والمحتوى المخفي والمعاينة الخاصة لا تظهر في الاستجابة العامة أو الكاش.
6. يمكن استخدام نفس رابط الصفحة المختصر داخل مدرستين دون تعارض.
7. الحفظ في المسودة لا يغير النسخة العامة؛ النشر والاسترجاع يعملان للمحتوى والمظهر.
8. الرسائل وطلبات القبول والوسائط تذهب إلى المدرسة الصحيحة.
9. طلبات متتابعة لمدارس مختلفة تحت SSR/Octane لا تتبادل الهوية أو البيانات.
10. القالب يعمل بالعربية والإنجليزية وعلى الهاتف، ويستخدم ألوان المدرسة في الوضعين.
11. بناء المتصفح وSSR وملف Vite manifest يتم التحقق منها قبل اعتماد النشر.

## ترتيب الأولوية والقرارات المتبقية

الأولوية: عزل المدارس وتحديد النطاق، ثم الصلاحيات، ثم تجربة التخصيص، ثم
المسودات والنشر، ثم التشغيل والإطلاق. لا يبدأ تصميم حر واسع أو تكامل اشتراكات
قبل نجاح اختبارات العزل الأساسية.

قبل التنفيذ يُحسم اسم نطاق المنصة، وعدد القوالب الابتدائية، وإتاحة النطاق
المخصص في النسخة الأولى، ومن يملك صلاحية النشر داخل المدرسة. القرارات أعلاه
اقتراحات للتخطيط، ولا تمثل تفعيلًا أو ربط نطاق أو تعديل صلاحيات.

لم تُنشأ جداول أو ترحيلات، ولم يُعدّل كود التطبيق أو إعداداته لتنفيذ SaaS.
